# Target: Code → spec annotations (spec-ID comments at enforcement sites)

## Current statement

**PARKED — do not engage until worker-v2 (close-domain + compliance) has baked
in real-world use.** Deliberate iteration discipline: one discovery mechanism
ships and proves itself before the next is added.

Plain comments carrying a spec ID at code enforcement sites (e.g.
`// SPEC-arch-001: server binds 127.0.0.1 only`) give the reverse mapping —
code → spec — with context locality: the invariant is in the implementer's
view at the exact moment the governed code is edited. Deliberately bare
comments: no syntax, no tooling coupling; greppable, and the hub already
auto-links spec IDs.

Sketched rules (to re-validate at engage time against worker-v2 experience):
- Organic authoring, no backfill: work-item-close annotates enforcement or
  fragile sites it materially touches; sparse and load-bearing, never blanket.
- Consumption: close-domain's per-work-item discovery and guardian audit grep
  target files for spec IDs; hits are highest-confidence candidates.
- Hard rule: absence of an annotation means nothing — annotations accelerate
  discovery, never define coverage.
- Hygiene: lint-check flags annotation IDs that resolve to no active,
  archived, or aliased spec item (typo catcher).
